# CPGames_bot

`CPGames_bot` получает новые комментарии VK с помощью периодического опроса (polling), формирует предлагаемый ответ для SMM-специалиста с помощью LLM, используя Google Sheets как источник знаний, и отправляет комментарий вместе с предложенным ответом SMM-специалисту в Telegram. Параллельно существующая FastAPI-панель доступна SMM-специалисту через браузер.

## Структура исходников

Основные Python-модули проекта находятся в пакете `src/`:

```text
src/
├── main.py
├── bot.py
├── config.py
├── models.py
├── vk_parser.py
├── gsheets_manager.py
├── games_data.json
└── ...
```

Запускайте модули из корня репозитория как пакет: `python -m src.main` и `python -m src.bot --watch`. Каталоги `data/` и `templates/` остаются в корне проекта.

## Обязательная production-конфигурация

Смотрите `.env.example`. Для основного production-сценария должны быть указаны реальные значения:

```dotenv
POSTGRES_DB=cpgames
POSTGRES_USER=cpgames
POSTGRES_PASSWORD=<strong-password>
POSTGRES_HOST=postgres
POSTGRES_PORT=5432

VK_GROUP_ID=...
VK_ACCESS_TOKEN=...
CHECK_INTERVAL=60
VK_COMMENT_MERGE_WINDOW_SECONDS=180
VK_FETCH_THREAD_REPLIES=true
POSTS_COUNT=3

TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...

LLM_API_URL=...
LLM_API_KEY=...
LLM_MODEL=...

GOOGLE_SHEETS_ID=...
GOOGLE_SHEETS_CREDENTIALS=credentials.json
```

Рекомендуется использовать `CHECK_INTERVAL=60`. Значение `43200` означает интервал в 12 часов между проверками и не подходит для своевременных SMM-уведомлений.

`VK_COMMENT_MERGE_WINDOW_SECONDS=180` объединяет подряд идущие комментарии одного VK-пользователя в одном посте, если они отправлены не более чем через 180 секунд друг после друга. Свежий комментарий удерживается до окончания этого окна и остаётся непомеченным в state-файле, поэтому продолжение, пришедшее уже в следующем polling-цикле, всё равно может быть объединено. AI получает единый текст и формирует один ответ. Значение `0` отключает и ожидание, и объединение. Комментарии разных авторов, разных постов, с разными `reply_to` или разделённые чужим/служебным комментарием не объединяются.

`VK_NOTIFY_EXISTING=false` — безопасное production-значение по умолчанию. При первом запуске парсер проверяет заданное количество последних постов и сохраняет идентификаторы всех уже существующих комментариев, не отправляя их в Telegram. Новыми считаются только комментарии, появившиеся после формирования этого начального состояния. Устанавливайте `true` только в том случае, если нужно повторно обработать и отправить исторические комментарии.

Комментарии VK загружаются постранично, по 100 комментариев за запрос. При `VK_FETCH_THREAD_REPLIES=true` (значение по умолчанию) парсер дополнительно обходит ветки `thread` через `wall.getComments(comment_id=...)`, поэтому обрабатывает не только верхний уровень, но и ответы внутри веток, включая ветки длиннее 100 ответов.

## Production в Docker

Обязательные сервисы — `postgres` и `app`. Для штатного production-деплоя используйте:

```bash
./deploy/deploy.sh
```

`deploy/deploy.sh` сначала поднимает внутренний PostgreSQL, останавливает writers, затем запускает одноразовую безопасную миграцию `/app/data/posts.db` → PostgreSQL. Если PostgreSQL уже содержит данные, старый SQLite повторно не импортируется. PostgreSQL не публикует порт `5432` наружу VPS.

Сервис `app` запускает:

```text
python -m src.main
```

FastAPI по-прежнему слушает `8000` внутри контейнера, а Docker публикует его на HTTP-порту `80` VPS:

```text
http://161-97-72-91.sslip.io
```

Это существующая SMM-веб-панель из `templates/index.html`; файл шаблона для публикации панели менять не требуется. HTTPS/Caddy и VK Callback API для этой схемы не нужны. Для внешнего доступа TCP-порт `80` должен быть разрешён в firewall VPS/провайдера.

Проверка состояния:

```bash
docker compose ps
./deploy/verify_deployment.sh
docker compose logs --tail=250 app
```

## Переход с SQLite на PostgreSQL

При первом деплое версии с PostgreSQL миграция выполняется автоматически после остановки `app`/`telegram-parser` и до повторного запуска приложения. Скрипт `python -m src.migrate_sqlite_to_postgres`:

1. создаёт таблицы PostgreSQL;
2. проверяет, что целевая БД ещё пуста;
3. создаёт `/app/data/posts.db.pre-postgresql-<timestamp>.bak`;
4. переносит `posts`, `comments`, `prompts` одной транзакцией;
5. восстанавливает PostgreSQL sequences для `id`;
6. сравнивает количества строк SQLite/PostgreSQL.

После деплоя проверка БД:

```bash
./deploy/verify_database.sh
docker compose ps
docker compose logs --tail=100 postgres app
```

Legacy-файл `posts.db` и его backup не удаляйте сразу. После нескольких успешных дней работы PostgreSQL их можно оставить только как архивную резервную копию.

## Telegram-уведомление для SMM-специалиста

Для каждого нового комментария VK/Telegram модуль `src.main`:

1. сохраняет комментарий в PostgreSQL;
2. определяет тему или намерение комментария;
3. подключает только нужный контекст: FAQ, данные игры и/или текст родительского поста;
4. передает выбранный контекст настроенной LLM для формирования предлагаемого ответа;
5. отправляет в Telegram-бот площадку, исходный комментарий, ссылку, автора и предложение AI;
6. добавляет кнопку `✅ Ответил` для SMM-специалиста.

Пока комментарий имеет статус `new` и не отмечен обработанным, фоновая синхронизация
повторяет уведомление. Нажатие `✅ Ответил` переводит комментарий в обработанный статус и
останавливает повторные напоминания. Исторический baseline повторно не рассылается.

LLM только подготавливает предложение ответа и не публикует его автоматически в VK.

### Контекстная генерация AI-ответа

AI-помощник сначала определяет намерение комментария и только затем выбирает контекст.
Благодарности и нейтральные реакции не превращаются в вопрос «о какой игре речь»;
проблемы оплаты обрабатываются как вопросы оплаты; для вопросов по игре/доставке может
использоваться полный текст исходного поста и релевантная информация из Google Sheets.
Для оплаты/общих технических вопросов игровой контекст из поста не подмешивается только
из-за того, что пост посвящён конкретной игре. Название игры запрашивается только когда оно
действительно необходимо и не определяется из самого комментария или поста.

### Короткие вопросы под постом

Короткие контекстные вопросы (`Сколько стоит?`, `Когда выйдет?`, `Есть на русском?`,
`Можно вдвоём?`, `Где купить?`, `Есть в наличии?`) используют родительский пост,
чтобы определить объект вопроса без шаблонного уточнения «о какой игре речь». При этом
общие вопросы вроде «У вас есть вакансии?» и независимые технические проблемы не получают
игровой контекст автоматически. Вопрос о релизе не подменяется сроком доставки.

### Контекст коротких вопросов

AI-маршрутизация учитывает, что вопрос в комментарии важнее благодарности: например, `Спасибо! Когда выйдет?` обрабатывается как вопрос. Короткие вопросы `Когда будет?`, `Когда появится?`, `А сколько?` используют контекст родительского поста, поэтому бот не должен автоматически просить уточнить название игры.

### Оперативный FAQ для проблемных и новых проектов

Для текущих статусов используется единый вертикальный блок внутри вкладки проекта в разделе
`📚 KNOWLEDGE_BASE (База знаний для бота)`. Парсер также сохраняет совместимость со старым
заголовком `📚 FAQ / ОПЕРАТИВНАЯ БАЗА ДЛЯ БОТА`:

```text
question        — сценарий/тип вопроса пользователя
keywords        — варианты формулировок и ключевые слова
content         — готовая публичная формулировка ответа
project_status  — текущий внутренний статус проекта
sent            — что уже отправлено/выполнено
not_sent        — что ещё не отправлено/не выполнено
next_step       — следующий шаг/ориентир
updated_at      — дата ручного обновления
internal_note   — инструкция SMM (не цитируется пользователю дословно)
content_type    — operational_faq
is_active       — TRUE/FALSE
```

`is_active=FALSE` — безопасное значение для незаполненной/непроверенной записи. После того как
SMM сверил факты и дату, запись можно включить `TRUE`. Оперативная запись имеет приоритет над
старыми общими полями и текстом поста при вопросах о сроках, статусе, регионах, отправке,
предзаказе, новых коробках и волнах. Оперативная запись используется только для совпавшего
проекта и подходящей темы (например, запись об отправке не подставляется в вопрос о новых
коробках). Если запись отключена/не проверена, бот не использует старый срок как текущий.
Если подтверждённой информации нет, бот не должен придумывать дополнения, «следующую волну»
или обещать «скоро».

Поле `aliases` в верхнем блоке вкладки позволяет указать альтернативные/локализованные названия
проекта через запятую или точку с запятой, чтобы короткий комментарий и текст поста корректно
сопоставлялись с нужной вкладкой.

### Комментарии, которые бот игнорирует

До вызова LLM отбрасываются:
- комментарии, опубликованные самой группой/брендом «Фабрика игр» (для VK основной признак —
  `from_id == group_id`);
- пустые и явно бессодержательные реакции вроде `Во, во!`, `ву-во`, `ага`, `угу`, `+1`,
  состоящие только из таких слов/символов.
Такие записи не создают Telegram-задачу SMM и не получают AI-ответ. Для Telegram worker
игнорируемый комментарий всё равно помечается просмотренным в state-файле, поэтому он не
появляется повторно на каждом цикле.
